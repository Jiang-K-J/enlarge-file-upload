# 前后端分片上传协议建议

本文说明应用如何为 `enlarge-file-upload` 设计后端协议。这些接口不是本包内置的 Node.js、Java 或 Go 服务端实现，接口路径和返回结构需要由业务自行定义。

## 为什么安装前端包还不够？

前端负责切分 `File`、调度并发请求、重试失败分片并展示进度。服务端仍然需要鉴权、安全地保存分片、查询已完成状态、合并文件和验证完整性。否则，暂停和恢复通常只能覆盖当前浏览器会话。

## 推荐流程

1. `POST /api/uploads/init`：校验业务身份，提交文件名、大小、类型和可选文件哈希；创建不可猜测的 `uploadId`，返回上传配置和已存在的分片索引。
2. `POST /api/uploads/chunk`：提交 `uploadId`、分片索引、分片内容和可选哈希；服务端以幂等方式保存分片。
3. `GET /api/uploads/:uploadId/status`：返回服务端已经持久化并确认的分片索引，客户端据此生成 `includeChunks`。
4. `POST /api/uploads/:uploadId/complete`：核对分片总数、分片大小和哈希，原子地合并最终文件，验证文件指纹并返回最终资源状态。

不要把客户端发出请求或显示 100% 视为服务端已经完成合并。业务完成状态应以 `complete` 接口的成功结果为准。

## 与客户端参数对接

`uploadFunction({ chunk, index, hash, cancelToken })` 用于调用业务的分片接收接口。

`startOffset` 适合已上传分片连续、只缺少尾部的情况。如果缺失索引不连续，优先使用 `includeChunks` 传入待补传分片。客户端应以服务端确认已经持久化的结果为准，不能只记录“请求已经发送”。

`onProgress`、`onSpeed` 和 `onEta` 用于展示浏览器端上传状态。它们不能代替服务端的合并进度和最终状态。

## 幂等与完整性

- 同一个 `uploadId + index` 重复提交时，应覆盖临时分片或返回已经完成，不能产生重复分片。
- 服务端校验分片索引范围、预期大小和实际读取长度。
- 如果使用分片哈希，服务端需要自行重新计算并比对，不能信任客户端提交值。
- 合并前检查分片是否齐全，合并后计算最终文件哈希。
- 最终文件写入临时路径，验证成功后再原子移动到正式位置。

## 安全与资源限制

- 所有上传接口重新校验登录状态、文件权限和租户边界。
- `uploadId` 使用不可猜测值，并绑定用户、租户和目标业务对象。
- 服务端限制单文件大小、分片大小、分片数量、总磁盘用量和并发请求数。
- 临时文件使用隔离目录和服务端生成的文件名，防止路径穿越和任意覆盖。
- 不依据文件扩展名信任内容类型；按业务风险执行内容检测和安全扫描。
- 设置未完成任务的过期时间，定期清理垃圾分片和失败任务。
- 生产环境使用 HTTPS，错误响应不暴露服务器路径、堆栈或内部凭据。

## 示例响应结构

下面只展示字段关系，不代表本包强制的协议：

```json
{
  "uploadId": "server-generated-id",
  "chunkSize": 5242880,
  "uploadedChunks": [0, 1, 4]
}
```

客户端根据 `uploadedChunks` 和总分片数计算缺失索引，再将缺失索引交给 `includeChunks`。
